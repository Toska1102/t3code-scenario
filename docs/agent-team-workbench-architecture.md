# Agent 团队工作台整体方案

**前端保留现有工作台的页面和交互，后端在完整 T3 Code 服务中增加工作台业务模块。** 工作台维护团队、项目、组织规则、任务工作流版本、具体任务和正式结果。T3 Code 执行步骤、启动和管理 Agent 会话、持久化运行、等待人工答复并发布执行事件。前端只访问工作台的 HTTP 和事件接口。

本方案以 [《Agent 团队工作台需求规格》](agent-team-workbench.md) 为逐控件验收清单，以 [Pencil 设计稿](Design.pen) 和 [HTML 导出](design-html/index.html) 为界面与跳转基线。部署决策按首版单运行设备、手动派发、所有已认证工作台用户同为管理员设计。运行设备仍需凭据和访问控制。工作台的组织岗位和评审负责人决定责任归属，用户权限模型无需单独定义多种角色。

仓库根目录的 T3 Code 是不可独立构建的学习副本。以下目录是落地后的目标结构，T3 运行相关的复用必须在完整 T3 Code 环境验证。现有独立 Next.js 原型保留作界面与交互参考。[仓库说明](../README.md)

## 1. 产品入口与严格验收

任务直接属于项目。任务工作流定义做法，历史任务引用派发时的确切版本。项目详情用两个并列模块呈现「任务工作流」和「项目任务」，前者包含「描述要做的事」。流程卡显示调用此流程的任务；任务显示所用版本并可反向打开。组织架构和 Agent 连接都由按钮唤起弹窗。首页展示团队卡及下属项目；项目列表与项目详情分别提供浏览和操作入口。

## 2. 目录与依赖方向

以下目录相对于**完整 T3 Code 工作树**。工作台前端独立于 T3 原有页面，后端使用 T3 现有运行进程，首版不增加另一个 Agent 调度进程。

      workflows/                       # 流程草稿、成员选择、画布和步骤属性
      dispatch/                        # 首次与再次派发的共用表单
      tasks/                           # 进度、活动、评审、会话、结果
      agents/                          # Agent 连接弹窗
    lib/
      workbench-client.ts              # 请求、订阅、错误映射
  server/                              # 完整 T3 服务进程
    src/
      workbench/
        bootstrap.ts                   # 组装数据库、T3 运行、HTTP 和事件接口
      workflows/                       # 已有 T3 运行定义、引擎和存储

  workbench-contracts/
    src/                               # 请求、响应、错误码、事件与运行状态的传输契约
  workbench-core/

文件名是接口责任的示例。每个用例可以有自己的文件，类型或私有辅助函数随用例放置，等出现明确复用再提取。首版只实现 SQLite。选择 Postgres 时，新增存储适配器并在 `bootstrap.ts` 切换组装，保留核心用例与同一套存储契约测试。

| 层 | 负责什么 | 可依赖的方向 |
| --- | --- | --- |
| 领域 | 组织图是否合法、工作流能否确认、哪个产出需评审、结果何时可完成。 | 领域自己的值与规则。输入用普通类型。独立于 React、传输、SQL、Effect 与 T3。 |
| 应用 | 读取快照、调用规则、组织事务、记录回执或运行结果。定义它实际需要的存储和运行接口。 | 自己的领域、应用层公开接口。跨业务模块经公开查询或快照，禁止读其他模块的私有存储。 |
| 适配 | HTTP 路由、SQLite、Pencil 所需前端数据、Agent 执行、观察、文件、YAML 与 LLM。 | 实现应用层接口。可依赖各外部库。传输类型仅在前端和适配层使用。 |
| 组装 | 选择具体存储、凭据与 T3 运行实例，连接适配器和用例。 | 可依赖各层公开接口，为唯一知道全部实现的位置。 |

输入流向是 `网页 → HTTP/事件适配器 → 应用用例 → 领域`。应用通过声明的接口调用存储与运行适配器。由 T3 回来的事件也从运行适配器进入用例，经过状态校验后更新工作台视图。浏览器没有 T3 原始命令、SQL、LLM 密钥或本机凭据。

**画布接入引擎的方式**。在完整 T3 服务中装入一个固定、受信任的工作台执行定义，用结构化的流程版本、步骤、依赖、参数和文件引用作为输入。选择执行定义时传明 T3 的执行器版本；选择用户工作流时传明工作台的业务版本 ID。固定执行定义按 DAG 调用 T3 的持久 `step`、`agent` 和 `ask`，步骤及尝试的执行名可稳定重建。工作台版本用于业务快照，T3 执行器版本用于重放软件行为。正式接入前需要验证自带定义的注册位置、运行恢复与并行执行。T3 现有定义加载器会实际导入 TypeScript，用户画布、YAML 和模型输出都作为数据校验，避免进入源码保存接口。[T3 定义加载](../apps/server/src/workflows/WorkflowRuntime.ts#L130) · [T3 工作流能力](user/workflows.md)

## 4. 四个核心用例与失败恢复

### 前后端接口与数据归属

| 场景 | 工作台接口 | 权威数据 |
| --- | --- | --- |
| 团队、项目、组织设置 | 团队总览、团队项目列表、项目概览、项目保存、组织草稿与保存、YAML 预览与导出。 | 工作台团队、项目、组织修订。项目与 T3 运行环境及其项目标识的映射保存在服务端。 |
| 流程创建与修订 | 获取草稿或确切版本，按草稿修订保存，生成建议，确认，列出版本调用。 | 工作台工作流和版本、字段定义、步骤依赖。调用清单根据任务的版本引用聚合。 |
| 派发、评审和结果 | 派发预检、派发提交、评审提交、结果保存重试、结果读取与文件下载。 | 工作台任务、提交回执、评审负责人和结果登记。T3 持久等待为评审能否被当次运行接受的依据。 |
| 进度、活动和会话 | 任务详情快照、按任务订阅增量、指定任务会话发消息。首版可用 SSE 推送进度并用 HTTP 提交。 | T3 的运行、步骤及线程状态映射为工作台事件，AgentTrail 活动可独立缺失。取消订阅或断线重连后重新读取快照。 |
| Agent 配置 | 列出实例、修改运行设置、检测及模型管理。 | 运行设备上的 T3 实例和密钥存储。返回脱敏摘要。工作台保存对实例和模型的引用及启用策略。 |

请求中的项目、任务、版本和会话 ID 都由服务端校验归属。任务详情先返回与同一事件游标对应的快照，再消费其后的事件。事件断档时重新读取快照。页面只把错误码映射到字段或步骤，确认和派发条件仍由后端裁决。前端与后端可分别部署，同域反向代理可简化登录与订阅。

### 确认流程

`ConfirmWorkflow` 接收草稿及其修订、项目 ID 和操作者，从仓库读取相关组织。领域检查名称、组织绑定、节点依赖、必审覆盖和输入输出，成功时保存不可变版本。只确认期间 Agent 暂时离线仍可成功。更新同一草稿时以修订号识别冲突，用户仍能恢复自己的修改。历史任务看原版本；当前流程以显式修订生成新版本。

### 手动派发和启动

`DispatchTask` 同时服务首次派发、流程卡派发、任务再派。读取当前组织修订和精确工作流版本，检查本次材料、设备目录、实例、模型和能力。在线检测允许在事务前完成。在一个业务存储事务中复核用于校验的组织修订仍是当前修订，保存必要的新确认版本、任务快照和启动意图。若修订在期间变化，以新修订重查或给出可恢复错误。首次派发前的业务校验失败时无版本半确认。提交成功后任务可短暂显示「正在启动」。

提交的启动意图在事务提交后交 T3，键固定为该具体任务的启动键。若启动已到 T3 但响应丢失，重试同一个键并认领原运行 ID。若 T3 暂不可用，任务保留在「待处理」，用户可重试同一个任务。不能把跨进程的启动成功承诺成一次数据库事务。事务内的正式业务记录和不可变启动键保证重试可恢复。每个尚未启动的 Agent 步骤在真正开始前再检查实例。用户后来停用实例时，该步骤进入待处理，保留既有产出。已启动的步骤继续使用其启动配置。[T3 幂等启动](../apps/server/src/workflows/WorkflowEngine.ts#L280)

### 管理员评审

`DecideReview` 使用已认证操作者、任务、步骤和尝试标识。只有当前待评审才可提交。指定人员用于「待我处理」，其他管理员可代办。通过后只解锁依赖满足的步骤。退回要求原因和返工目标，形成新尝试，失效受影响下游的旧通过，保留独立并行分支。使用 T3 的当前等待答复能力防止旧答复落到新一轮。先保留决定和提交标识，再通过 T3 确认状态，失败可用同一决定核对或恢复。运行时与用户界面都关联到同一个评审尝试。

### 结果交付

`SaveTaskResult` 只接受步骤已完成且当前产出满足评审的任务。文件先通过工作台文件适配器保存并校验，之后将结果清单和完成状态一起登记。页面「查看结果」打开该任务的正式结果，文本查看、文件下载、输入、执行版本与评审记录从同一入口可查。文件或登记失败时保持「待处理」，重试保存同一产出，不重跑已成功步骤。完成后的暂时读取错误只影响可读性。幂等登记以任务及最终产出为键；未登记的临时文件走回收策略。

## 5. 怎么快速改，最少读什么，改动波及哪里

三个问题对应三个可检查要求。**先从界面动作找到用例，靠用例和测试理解规则，用公开接口限制连带修改。** 对照表就是入口索引，测试按用例与画板定位。下面以已经出现的真实变化检验目录是否够清楚。

| 后续改动 | 从哪里进 | 最少先读 | 预期改动范围 |
| --- | --- | --- | --- |
| 修改「待我处理」统计 | 02.01 → 项目概览查询 | `ProjectOverview`、评审投影字段及该查询验收 | 业务查询与测试；若原响应已含计数，页面接口无需变化。 |
| 修改确认时的必审覆盖 | 03.01 → `ConfirmWorkflow` | `WorkflowDefinition` 的确认规则及必审回归 | 工作流领域与测试；派发调用同一规则自动生效。若契约新增错误码，才调对应 UI 提示。 |
| 修复新规则生效后打到旧快照 | 03.02 → `DispatchTask` | 用例、组织修订读写接口、存储事务契约和预检竞态测试 | 派发用例和存储实现，可保持 T3 运行、页面和历史任务查询接口。 |

限制改动范围靠两项验收。第一，依赖检查拒绝领域引用 React、SQL、网络或 T3，拒绝用例直接导入具体适配器。第二，用例测试跨生产接口，存储替换重跑同一组事务和幂等测试，页面用画板验收验证实际行为。这样修改一条业务规则时可以先读其用例和测试，只有失败跨过接口才继续追下层。

## 6. 编码前的 LLM × SMT 和开工验收

本轮先从应用用例和 T3 运行时两种视角推演，再把两边可能同时成立的假设交给 Z3 4.13.4。以下五组反例通过逐项删减得到包含意义下最小冲突集。改用表中的决策后，每组均复验为 SAT。

| ID | Z3 判定为 UNSAT 的最小冲突集 | 采用方案 |
| --- | --- | --- |
| A01 | 历史任务使用版本 1；执行版本必须等于该版本；实际启动默认选版本 2。 | 显式指定执行器版本并绑定业务版本快照。 |
| A02 | 业务启动意图已回滚；启动要求已提交意图；仍执行了启动。 | 提交后才消费持久启动意图；稳定键支持恢复。 |
| A03 | T3 已结束；正式结果保存失败；工作台完成必须已有结果；T3 结束直接设置工作台完成。 | 运行结束和交付完成分别记录。「已完成」以正式结果登记为准。 |
| A04 | 旧批准绑定尝试 1；当前产出是尝试 2；交付需要当前尝试的批准；复用旧批准直接交付。 | 受影响的新尝试重新进入评审。 |
| A05 | 同一提交必须返回同一任务；重试每次创建新任务。 | 按提交标识保存任务回执；T3 运行另有稳定启动键。 |

在正式开始代码生成前，将需求规格的 R01–R13、D01–D11 及本方案的 A01–A05 写成可重复执行的模型与验收条目。LLM 分别从控件和实体状态推导，按分歧单独建模。保留假设、正例、反例、核心冲突集和裁决，无法解释的 `unknown` 或仍可成立的反例先回到规格。SMT 检查只覆盖建模条件，运行时事务、并行、凭据、文件隔离与会话恢复需要真实集成验证。[需求校验记录](agent-team-workbench.md#9-编码前的-llm-与-smt-校验)

### 实施顺序和交付门槛

1. **先验证 T3 接入链。** 在完整 T3 工作树中注册固定执行器，用真实 Provider 实例完成 Agent 步骤、并行汇合、人工评审及一次服务重启恢复。验证步骤会话、附件输入、幂等启动和能力错误有明确映射。该阶段的接入结论决定是否采用上述进程组装方式。
2. **再建立业务接口。** 实现 SQLite、确认/派发/评审/结果用例和持久启动。使用同一接口测试组织变更、审阅尝试、持久化失败、重试和事件乱序。工作台先完成一个简历审核的真实纵切，回归之后再替换其他原型入口。
3. **最后逐页收齐设计稿。** 保留现有页面和部件，接入真实接口。对全部画板与补充状态检查可见控件、权限及失败恢复。执行入口不并行保留两套生产实现。发布前逐项验收三种 Agent 和十张画板，模拟器可继续用于本地测试。

当前交付为需求落地与目录方案。完整 T3 中固定执行器的注册、附件访问、硬限制执行、真实 AgentTrail 关联和生产浏览器验收仍待验证。未新增业务代码或改动画板。
